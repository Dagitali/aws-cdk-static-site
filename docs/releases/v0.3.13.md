# AWS CDK Static Site v0.3.13 (Planned)

The planned version 0.3.13 standardizes this repository's GitHub Actions and supporting governance
documents with the conventions used by other Dagitali Python projects. No `v0.3.13` tag has been
created yet.

## Highlights

- Establishes `pr.yml`, `ci.yml`, `sbom.yml`, and `cd.yml` as the shared minimum workflow set for
  Python projects while keeping their responsibilities distinct.
- Adds a dedicated pull-request policy workflow that enforces the repository's GitFlow paths for
  `develop` and `main`, including the same-repository requirement for release and hotfix branches.
- Aligns workflow names, run names, trigger organization, permissions, concurrency, documentation,
  and immutable-action-pin conventions with sibling Dagitali Python projects where their behavior
  is shared.
- Adds EPUB and external-link checks to pull-request CI and validates tagged HTML and EPUB builds
  before release publication.
- Expands reusable branch-protection, maintainer, pull-request, release-note, and Mermaid guidance,
  including explicit required-check candidates, advisory checks, and branch-creation examples.

## Change Scope

The new `.github/workflows/pr.yml` owns hosted pull-request routing. It accepts documented feature,
bugfix, maintenance, dependency, and synchronization branches into `develop`; accepts only
same-repository `release/*` and `hotfix/*` branches into `main`; and reports a compatible result for
merge-queue validation.

The `ci.yml` workflow remains the comprehensive validation gate. Its required validation job covers
repository policy, linting, type checking, tests with coverage, example synthesis, and strict
HTML documentation builds. Separate jobs validate EPUB output and external links. Existing
supported-Python and dependency-boundary matrices, cross-platform installation checks, and
distribution validation remain intact. The `sbom.yml` workflow continues to generate the package's
Python dependency inventory, and `cd.yml` validates tagged HTML and EPUB documentation before it
publishes artifacts from existing annotated semantic-version tags.

The workflow map, README status badges, branch-protection policy, maintainer runbooks, release-note
template, and pull-request template now describe the same responsibility boundaries. Copilot-facing
Mermaid instructions were added for consistent validation and preview of repository diagrams. The
release-note template now consistently serves both the detailed versioned document and the reviewed
notes for the canonical GitHub Release. Pull-request instructions are non-rendered comments so the
submitted description retains the shared structure without carrying template guidance forward.

This release does not change package source, runtime dependencies, public exports, construct
configuration, synthesized CloudFormation behavior, or AWS resources.

## Compatibility and Configuration

No consumer compatibility or construct configuration changes are required. Maintainers should run
the renamed `Guard pull request target` and `Validate pull request` jobs on representative pull
requests before replacing any existing required-check names in GitHub rulesets.

The pull-request guard intentionally recognizes the repository's documented branch families.
Exceptional `support/*` branches require a separately reviewed guard and protection-policy update
before use.

## Support Boundary

No Python, AWS CDK, package, stability, or infrastructure-support boundaries change in this
release. The project remains a Python-only package even though the workflow organization is aligned
with a website repository that also manages npm dependencies and production deployment.

## Validation

- `actionlint .github/workflows/*.yml` passes for the standardized workflow set.
- Repository pre-commit checks pass for the changed workflows and Markdown documents.
- The immutable GitHub Actions pin and supported-Python policy checks pass.
- `make check` passes with 65 unit and integration tests, 100% measured coverage, distribution
  builds, and `twine check` validation.
- Strict Sphinx HTML, EPUB, and external-link documentation checks pass with warnings treated as
  errors. The network-dependent external-link result remains advisory by default in hosted CI.
- The release branch must still pass its hosted PR, CI, dependency-matrix, cross-platform, and
  distribution jobs before merge.

## Deployment and Rollback

Merging this release into `main` does not deploy AWS resources. Creating the annotated `v0.3.13`
tag triggers `cd.yml`, which rebuilds and validates the source distribution and wheel, generates
checksums and a CycloneDX SBOM, validates tagged HTML and EPUB documentation, and attaches the
artifacts to the corresponding GitHub Release. The workflow does not publish to PyPI.

If the new workflow boundaries or required-check names cause a repository-governance regression,
restore the prior workflow and ruleset configuration through a reviewed hotfix. Existing package
artifacts and deployed consumer infrastructure do not require rollback because runtime and
synthesized behavior are unchanged.

## Known Limitations and Follow-Up

- Workflow and job names must appear in at least one representative hosted run before maintainers
  can safely select their exact emitted check names in branch-protection rulesets.
- Production planning, npm SBOM generation, website monitoring, and AWS deployment remain
  intentionally specific to `dagitali.com` and are not copied into this reusable construct package.
- ETLPlus-specific lockfile enforcement, CLI and installer smoke tests, Codecov reporting,
  Read the Docs integration, and PyPI publication remain outside this package's workflow scope.
- PyPI publication remains intentionally disabled pending a reviewed trusted-publishing workflow
  and protected environment.
