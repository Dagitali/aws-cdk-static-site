# AWS CDK Static Site v0.3.22

Version 0.3.22, tagged on 2026-09-27, completes the migration of repository-policy checks to the
pinned Popo CLI and removes the deprecated local compatibility implementation.

- [Highlights](#highlights)
- [Change Scope](#change-scope)
- [Compatibility and Configuration](#compatibility-and-configuration)
- [Support Boundary](#support-boundary)
- [Validation](#validation)
- [Deployment and Rollback](#deployment-and-rollback)
- [Known Limitations and Follow-Up](#known-limitations-and-follow-up)

## Highlights

- Uses the pinned Popo CLI as the authoritative implementation for dependency-boundary, Markdown,
  GitHub Actions pin, Python-policy, and release-changelog checks.
- Preserves the existing Make targets as the stable contributor interface across local hooks,
  continuous integration, and tagged-release validation.
- Removes the deprecated repository-local `scripts` package and its duplicate regression tests after
  the Popo-backed gates completed their migration window.

## Change Scope

Repository-policy behavior now comes exclusively from the reviewed Popo revision declared in the
development dependencies and configured by `[tool.popo]` in `pyproject.toml`. Make, pre-commit,
continuous integration, and release automation use that implementation, while
`tests/integration/test_popo.py` retains this repository's consumer configuration and automation
contracts.

The obsolete `scripts` package, its command dispatcher and support helpers, and seven direct unit
test modules are removed. Make no longer includes the deleted directory in cleanup or strict typing
paths. Architecture, contributor, testing, agent, and decision documentation now describe Popo as
the sole repository-policy implementation.

This release does not change package source, public exports, construct properties, construct IDs,
runtime dependencies, synthesized CloudFormation behavior, AWS resources, workflow permissions,
release artifacts, or publication mechanics.

## Compatibility and Configuration

No consumer compatibility or configuration changes.

The removed `python -m scripts` interface was an internal, deprecated compatibility surface.
Maintainer automation that still invokes it must use the corresponding Make target or `python -m
popo` command. Contributor environments continue to require Git access to install the pinned Popo
development dependency until Popo is published to a package index.

## Support Boundary

No Python, AWS CDK, package, service, region, or infrastructure-support boundaries change in this
release. Popo governs repository maintenance only and is not a runtime dependency of the construct.

## Validation

- All Popo-backed repository-policy gates pass.
- The default unit and integration suite passes with 50 tests and 100% measured coverage.
- Formatting, linting, strict typing, dependency-boundary, Python-policy, Markdown-reference, and
  immutable-action-pin checks pass.
- Strict HTML and EPUB documentation builds pass.
- The source distribution and wheel build successfully, pass `twine check`, and pass all four
  package-artifact tests without the retired compatibility package.
- The dated changelog section, release-document links, and whitespace checks pass.
- Hosted release-candidate and clean distribution-installation checks must still pass on the exact
  commit promoted for release.

## Deployment and Rollback

Merging this release does not deploy AWS resources. Creating the annotated `v0.3.22` tag runs the
existing release workflow, which must validate and publish the GitHub Release artifacts before the
release is considered complete. PyPI publication remains disabled.

No CloudFormation resource replacement, data migration, DNS change, service interruption, or cost
change is expected. If the Popo-only maintenance path causes an unforeseen repository workflow
regression, revert the compatibility-surface removal and prepare a corrective patch release; package
consumers can remain on `v0.3.21` because runtime behavior is unchanged.

## Known Limitations and Follow-Up

- Popo remains installed from a pinned Git revision until it is published to a package index.
- External-link availability remains covered by the separate network-dependent documentation check.
- PyPI publication remains intentionally disabled pending a reviewed trusted-publishing workflow and
  protected environment.
