# AWS CDK Static Site v0.3.20 (Planned)

The planned version 0.3.20 aligns repository tooling and governance with reusable Dagitali
conventions while preserving the package's public API and synthesized infrastructure. No `v0.3.20`
tag has been created yet.

## Highlights

- Adds direct contracts for the shared Python setup action and repository-maintenance Make targets,
  including input validation, execution order, overridable commands, and cleanup path guards.
- Adds privacy-aware evidence-inventory and documentation-correction templates for reviewing public
  technical claims without exposing confidential material.
- Adds a change-management playbook and role-oriented documentation navigation that connect scope,
  ownership, verification, releases, and rollback.
- Simplifies pull-request routing so all ordinary, automated, and external branches may target
  `develop`, while `main` remains restricted to same-repository release and hotfix branches.

## Change Scope

Repository contract coverage now verifies that the local setup action validates its string-boolean
inputs before environment setup, conditionally installs the project, checks dependency integrity,
and reports the resulting environment in the intended order. Makefile contracts verify that cleanup
rejects paths outside the repository and that installation, formatting, and unit-test commands
remain overridable. A session-scoped `repository_root` fixture removes repeated path-depth
assumptions from these suites.

The new blank evidence inventory records source ownership, disclosure authority, verification,
limitations, metrics, and publication decisions for proposed public claims. A documentation issue
form provides a separate public intake path for accuracy, accessibility, compatibility, security,
privacy, and stale-reference corrections without inviting confidential or vulnerability evidence.

The change-management playbook routes maintainers through the existing impact map, API checklist,
documentation synchronization guide, runbooks, and release process. The documentation index adds a
role-oriented starting map and separates maintained guides from topic indexes.

The pull-request guard now reserves `main` for same-repository `release/*` and `hotfix/*` sources
without restricting source names targeting `develop`. Governance documents distinguish canonical Git
Flow roles from the permitted `chore/*`, `ci/*`, `docs/*`, `dependabot/*`, and `sync/*` repository
conventions, and retain `feature/*` as a tooling-compatible alternative.

This release does not change package source, public exports, construct properties, construct IDs,
runtime dependencies, synthesized CloudFormation behavior, AWS resources, release triggers, release
artifacts, or publication mechanics.

## Compatibility and Configuration

No consumer compatibility or configuration changes.

Contributors may continue using canonical Git Flow prefixes or the documented repository-specific
prefixes when targeting `develop`. Pull requests targeting `main` must still use a same-repository
`release/*` or `hotfix/*` branch. Maintainers may use either `sync/main-into-develop` or
`feature/sync-main-into-develop`, according to their Git Flow tooling.

## Support Boundary

No Python, AWS CDK, package, stability, service, region, or infrastructure-support boundaries change
in this release. `support/*` remains reserved for explicitly planned maintenance of an older release
line with an agreed base and integration strategy.

## Validation

- Focused setup-action and Makefile contracts pass.
- Formatting, linting, strict typing, dependency-boundary, Python-policy, Markdown-reference, and
  immutable-action-pin checks pass.
- `actionlint` accepts the pull-request workflow, and the workflow parses as YAML.
- The source distribution and wheel build successfully and pass `twine check`.
- The dated changelog section, release-document links, and whitespace checks pass.
- Strict HTML and EPUB documentation builds pass.
- Clean distribution-installation smoke tests and hosted release-candidate checks must still pass on
  the exact commit promoted for release.

## Deployment and Rollback

Merging this release does not deploy AWS resources. Creating the annotated `v0.3.20` tag runs the
existing release workflow, which must validate and publish the GitHub Release artifacts before the
release is considered complete. PyPI publication remains disabled.

No CloudFormation resource replacement, data migration, DNS change, service interruption, or cost
change is expected because construct source and synthesized behavior are unchanged. If the revised
pull-request policy disrupts contributor automation, restore the prior target cases or correct the
documentation through a reviewed patch release. Package consumers can remain on `v0.3.19` while a
correction is prepared.

## Known Limitations and Follow-Up

- Confirm the pull-request guard on representative `develop`, release, hotfix, external, and
  merge-queue events before making its result a required hosted check.
- External-link availability remains covered by the separate network-dependent documentation check.
- PyPI publication remains intentionally disabled pending a reviewed trusted-publishing workflow and
  protected environment.
